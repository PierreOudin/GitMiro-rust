# ADR-001: Tauri v2 + React/TypeScript

- Status: Accepted for the Rust port direction; validate with the first vertical slice.
- Date: 2026-11-04
- Owner: GitMiro Rust Port

## Context

GitMiro needs a desktop UI that preserves the current Compose application's screens, interactions, themes, keyboard behavior, and Git workflows. The application engine and Git integration move to Rust and Git CLI. The user confirmed Tauri v2 with React/TypeScript as the selected UI stack.

## Decision

- Tauri v2 owns the desktop window, native integration, and a restricted IPC boundary.
- React/TypeScript renders the UI in the system WebView.
- Rust owns application behavior, Git CLI calls, persistence, and OS integration.
- Git remains the source of truth for repository state.

## Consequences

- Reuse CSS and HTML layout for close design-system fidelity; match existing Graphite colors, Geist typography, density, menus, and dialogs.
- Treat frontend input as untrusted at every IPC command; expose narrow commands and capabilities.
- Validate WebView2 installation/runtime, packaging, startup time, idle/active memory, and interaction latency on supported platforms.
- Keep Kotlin behavior and its UI as the parity reference until replacement is complete.
- Keep the Kotlin release workflow during staging; at cutover, switch release packaging to Tauri and remove Kotlin/Gradle build steps only after migration gates pass.
- Reopen framework selection only if a concrete compatibility, licensing, accessibility, or measured performance issue blocks this stack.

## Validation scope

No competing framework prototypes. Validate a small Tauri/React/Rust vertical slice against the current application, then measure representative flows and process-tree resource usage. Preserve every platform currently supported by the existing release configuration unless the owner approves a change.

## Windows baseline snapshot

- Run: 2026-11-05, Windows 11 build 26300, AMD Ryzen 7 7800X3D, 32 GiB RAM, Git 2.54.0.
- Corpus: temporary local repository with 1,000 commits, HEAD `9d8af30a5ee9376a7ab1921ac0f93bebe370a96c`; both apps opened the same repository. Tauri loaded both 500-commit pages.
- Builds: Tauri commit `f44fa385`; Kotlin source baseline `abde13a0` (GitMiro 2.0.1).
- Five process-tree samples, 3 s apart: Tauri median RSS 517.2 MiB / private bytes 300.4 MiB; Kotlin median RSS 391.4 MiB / private bytes 535.8 MiB. Tauri RSS is 32% higher; private bytes are 44% lower. Include descendant WebView2 processes in Tauri totals.
- One 20 s idle CPU window: Tauri consumed 0.24 CPU s; Kotlin consumed 0.00 CPU s at displayed precision. This single window is directional only.
- Initial-slice visual comparison: Kotlin showed commit graph and status/workflow panels; the first Tauri slice showed a commit list without custom graph drawing. This confirmed a major parity gap at that point; it did not demonstrate an overall performance win.
- Follow-up after this baseline: Tauri now draws merge-aware lanes across local branches, remote branches, and tags, with lane state preserved across pages. Branch/tag labels are present. Staged and unstaged panels show status; individual files can be staged or unstaged. File diffs and side-by-side conflict previews support choosing a whole current or incoming side, including delete/modify conflicts. Binary previews, per-block conflict editing, and stash remain to port. GM-63 adds staged-only commit, amend, persisted draft, author prompt/global save, configurable sign-off, hook errors, and repository refresh. Commit runs through Git CLI and leaves configured signing behavior intact; signed commits were not exercised. The earlier performance snapshot does not measure graph drawing.
- Graph follow-up: on the same 1,000-commit fixture and machine at `5d03950e`, five idle samples 3 s apart measured the Tauri **debug** process tree (app + six WebView2 processes) at median RSS 506.3 MiB / private bytes 270.2 MiB. The Kotlin app JVM alone measured 280.2 MiB / 537.2 MiB; its Gradle launcher/daemon were excluded. CPU rose 0.22 s for Tauri and 0.03 s for Kotlin over the 12 s window. This is diagnostic only: debug build, one warm run, and RSS depends on resident pages; repeat with release builds and cold-start/interaction measurements before drawing a performance conclusion.
- Release follow-up: on the same Windows machine and 1,000-commit fixture, `ba64399d` release build (unbundled) loaded the same 500-commit page as Kotlin baseline `abde13a0`. Five warm samples 3 s apart measured the isolated Tauri process tree (app + six WebView2 processes) at median RSS 465.2 MiB / private bytes 228.5 MiB; Kotlin app JVM + console host measured 281.4 MiB / 537.5 MiB, excluding Gradle wrapper/daemon. RSS was 65% higher for Tauri; private bytes 57% lower. Both idle CPU deltas rounded to 0.00 s over 12 s. This single warm release sample is directional only; cold-start, interaction latency, and graph-render cost remain unmeasured, so it does not establish a general performance win.
- Early CUA graph-render probe: release variants without graph (`510d9bb4`) and with graph (`af974512`) gave asymmetric single observations; those timing numbers are not comparable and do not support a performance conclusion. Temporary worktree/build artifacts were removed and not committed. Superseded by the controlled five-window steady-state probe below.
- Offscreen commit-list A/B: same Windows host, release build, 1,000-commit fixture, WebView profile, screenshot-only state, 7-process tree and 20 s CPU windows. Baseline CSS keeps `content-visibility` on the unmounted recent-repository list; history has none. Five baseline CPU samples: 3.66, 3.42, 3.19, 3.33, 3.11 s (median 3.33); private bytes 219.5, 216.9, 214.7, 216.8, 213.6 MiB; RSS 423.2, 421.2, 419.1, 421.3, 418.8 MiB. Exact current candidate uses `content-visibility: auto` and `contain-intrinsic-size: auto 50px` on `.commit-list li` (50 px inner tracks + 1 px border = 51 px row). Five candidate CPU samples: 1.53, 1.77, 1.42, 1.45, 1.27 s (median 1.45, −56%); private bytes 192.8, 190.2, 191.9, 189.3, 189.3 MiB (median 190.2); RSS 398.0, 391.9, 393.4, 391.0, 391.6 MiB (median 391.9). Sequential, warm, one-machine A/B; directional, not p50/p95. The earlier 51 px placeholder A/B is superseded. Large-log DOM virtualization and broader parity remain open.
- SVG graph probe: same release build, 1,000-commit fixture loaded, 7-process tree, screenshot-only and five 20 s warm windows per variant. No-shape variant kept an empty `<svg class="commit-graph">` so grid placement, width and height stayed identical; only graph shapes were omitted. CPU samples after rendering were 2.33/2.59/2.16/2.58/2.55 s without shapes (median 2.55) and 2.31/2.19/2.36/2.69/2.41 s with SVG shapes (median 2.36). Difference (0.19 s) is below per-variant spread; no steady-state CPU cost was isolated. This measures idle cost after the first render; it does not isolate initial SVG render or scroll-frame cost. One warm host; not p50/p95.
- Large-history CLI responsiveness probe: same Windows host, temporary 100,000-commit repository (pack 18.3 MiB), five fresh-process samples each. `git log -n 500 --format=%H` took 38.03–40.86 ms (median 40.05 ms); `git status --short` took 37.53–40.86 ms (median 38.68 ms). These timings include process startup and measure Git CLI only, not Tauri rendering, scrolling, or app responsiveness. Fixture stayed under `%TEMP%` and is excluded from Git.
- Current Windows package check, exact source `fa69b470`: `npm run tauri build` succeeded with `CARGO_TARGET_DIR` in `%TEMP%`, producing MSI (2.48 MiB) and NSIS installer (1.67 MiB) outside the repository. CI run `41980686887` passed Windows installer, Linux, macOS, and Gradle jobs at earlier source `fb6563cd`; exact-source CI run `41981569793` could not start because GitHub blocked jobs for account billing/spending-limit failure.
- Runtime accessibility spot-check on the exact Windows package and the temporary 1,000-commit repository: UI Automation exposed named Staged changes and Unstaged changes regions, counts, and commit history list. Tab from the focused repository heading moved visible focus to Open another. This is a keyboard spot-check, not a complete keyboard or screen-reader audit.
- Current structural UI comparison, Windows benchmark repository, exact Tauri package `fa69b470`: Tauri shows a centered repository heading, branch chip, staged/unstaged cards, and full-width commit graph/history. Kotlin shows its command toolbar, ref/navigation sidebar, and integrated staged area. A native folder picker obscured part of the Kotlin capture, and window sizes differed, so this is not a controlled pixel comparison. The visible shell mismatch remains open; do not claim visual parity from this slice.
- Kotlin stores recent paths as JSON in Java Preferences (`gitmiroConfig` / `lastOpenedRepositoriesList`); this staged Tauri slice stores its own recent paths in WebView local storage. Import the existing Kotlin value during final settings migration before Kotlin is removed; do not mutate Kotlin settings during staging.
- CI run `41942059184` passed Rust format/lint/tests, Windows installers, macOS/Linux Tauri builds, and Gradle build/tests.
- GM-66 comparison (2026-11-12, details in [perf/gm66-benchmark-report.md](perf/gm66-benchmark-report.md)): new machine (Ryzen 9 PRO 7940HS laptop, 62.7 GiB, Windows 11 build 26200, Git 2.51.0, AC, Balanced plan), so the figures above do not transfer. Kotlin 2.0.1 release package (`abde13a0`, official zip, hash verified) vs Tauri release build of `693d05b2` code, same 1,000-commit / 128-ref fixture (HEAD `1f252592...`), interleaved, 5 runs each (owner decision; 10 for the Tauri in-page scenarios and Git CLI). Medians, Tauri vs Kotlin: window visible 0.21 vs 2.60 s; repository ready 4.95 vs 3.41 s (Tauri includes the recent-entry click; one Kotlin outlier at 50 s not explained); file diff painted 1.92 vs 0.30 s; idle 5 min private bytes 228 vs 439 MiB, private working set 141 vs 337 MiB, working set 429 vs 403 MiB (+7%); idle CPU 0.3 vs 0.2 s per 60 s. Tauri in-page: open 2.95 s, diff 1.14 s, status refresh 0.73 s against 0.6 s, 45 ms and 47 ms for Git alone; scroll frames 16.7 ms p50 (0 over 25 ms), branch filter 32 ms. About 20 `conhost.exe` per repository open were observed; the release build started Git without `CREATE_NO_WINDOW`. Follow-up fix `f1793e27` sets that flag on every production Git spawn; one in-page re-run (3 repetitions, same machine and fixture) gave open 0.73 s, file diff 0.20 s, status refresh 0.11 s (p50), confirming the cause. Conclusion: the foundation is acceptable on memory, idle CPU and rendering; the full campaign (memory, CPU, startup, screen-captured times) still has to be re-run on the fixed build before any latency claim against Kotlin. Not measured: true cold start, Kotlin filter/scroll/status, commit selection (not ported), 100,000-commit app runs. Protocol and scripts: `docs/perf/gm66/`.
- Limits: one machine per campaign and one corpus per campaign; the earlier snapshots above have no p50/p95 and were taken on another machine. GM-66 adds p50/p95 on a second machine but still lacks a true cold start, a full keyboard/screen-reader audit and a 100,000-commit app run. Do not use these snapshots to claim the port meets performance goals beyond what the GM-66 report states.
